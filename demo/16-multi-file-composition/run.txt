===== [1] a component schema in its own file, usable on its own ==============

Every schema in the demos so far fit in a single file. This demo
splits one across two files: a component schema that stands
alone, and a composite schema that enforces the component's
requirements together with requirements of its own. The component
below describes one member, "id", a string, and requires it. It
is deliberately open: there is no closing keyword anywhere in it,
so members it does not describe are accepted.

Five instances are checked against the component. The first four
vary only members the component does not describe: "id" alone;
"note" beside it; "status" beside it; "id", "status", and "note"
together. The component accepts all four. The fifth has "status"
but no "id", and is rejected: the component is open about members
it does not describe, not about the one it requires.

The four accepted records return in the next section, checked
against the composite schema. These four already satisfy the
component's requirements, so every rejection there comes from a
requirement the composite adds -- and that openness is what lets
composites build on the component.

----- [2] the component schema -----------------------------------------------

$ cat requires-id-open.json
{
  "$id": "https://example.org/schemas/requires-id",
  "type": "object",
  "properties": { "id": { "type": "string" } },
  "required": ["id"]
}

----- [3] a record with id alone ---------------------------------------------

$ cat instance-id.json
{"id": "r1"}

----- [4] jsonschema (Python): id alone --------------------------------------

$ jsonschema-validate --schema requires-id-open.json --instance instance-id.json
VALID

===== [18] a composite schema that applies the component, adds a requirement, and closes the whole schema =====

The composite schema below applies the component schema with a
"$ref" in an "allOf" branch, naming the component by its "$id"
(demos 12 and 13). Beside the "allOf" it describes one more
member, "status", requires it, and closes the whole schema with
"unevaluatedProperties": false. To "unevaluatedProperties", a
member is extra only if no schema evaluated it (demo 15) -- and
the component, applied by the "$ref", evaluates "id". So "id" and
"status" are both admitted, and any other member is extra.

The --ref option loads a schema file and registers it under its
"$id"; a "$ref" naming that "$id" then resolves to it. Here each
validator is given the component that way. The "$id" is a name to
resolve against, not a URL anyone fetches (demo 13).

The same four instances, in the same order. The instance with "id"
alone is rejected for lacking "status". The instance with "id" and
"note" is rejected twice: "status" is missing, and no schema
evaluates "note". The instance with "id" and "status" passes. The
instance with "id", "status", and "note" is rejected for "note"
alone.

Everything the component accepted and the composite rejects comes
from the requirements the composite adds. The component file is
unchanged, still open, and still usable on its own, and stricter
schemas can be layered on it by reference, each in its own file.

----- [19] the composite schema ----------------------------------------------

$ cat requires-status-and-id-closed.json
{
  "$id": "https://example.org/schemas/requires-status-and-id",
  "allOf": [ { "$ref": "https://example.org/schemas/requires-id" } ],
  "properties": { "status": { "type": "string" } },
  "required": ["status"],
  "unevaluatedProperties": false
}

===== [28] with one component schema, the allOf is not strictly necessary =====

From the 2019-09 version on, a "$ref" can sit directly beside
other keywords and applies alongside them. The schema below is
identical to the composite except that the "allOf" is gone and the
"$ref" sits beside the other keywords. Checked against the
instance with "id" and "status" and the instance with all three
members, it returns the composite's verdicts exactly.

----- [29] the same composite, without the allOf -----------------------------

$ cat requires-status-and-id-closed-no-allof.json
{
  "$id": "https://example.org/schemas/requires-status-and-id",
  "$ref": "https://example.org/schemas/requires-id",
  "properties": { "status": { "type": "string" } },
  "required": ["status"],
  "unevaluatedProperties": false
}

===== [34] keep the allOf even so ============================================

Validators for the versions before 2019-09 ignore the members
beside a "$ref" -- silently, with no error and no warning. Handed
to one of them, the schema above enforces only the component
schema's requirements: "required": ["status"] and
"unevaluatedProperties": false simply vanish. The "allOf" form means the same thing in every version of
the language. A "$ref" beside the other keywords also stops at
one component: an object has at most one member named "$ref",
while an "allOf" holds a branch for each of any number of
component schemas. The composite keeps its "allOf" even though a
single component schema makes it optional.

===== [35] omitting the component file is an error, not a verdict ============

The composite's passing run again, with the --ref omitted. Both
validators refuse -- an error, not a verdict -- because the
composite's "$ref" now resolves to nothing. Ajv refuses while
compiling the schema, jsonschema during validation (demo 12). A
schema split across files is complete only when all of its files
are present, and the error is the reminder.

----- [36] jsonschema (Python): composite without --ref ----------------------

$ jsonschema-validate --schema requires-status-and-id-closed.json --instance instance-id-status.json
jsonschema-validate: error: requires-status-and-id-closed.json contains an unresolvable $ref: Unresolvable: https://example.org/schemas/requires-id

----- [37] ajv (JavaScript): composite without --ref -------------------------

$ ajv-validate --schema requires-status-and-id-closed.json --instance instance-id-status.json
ajv-validate: error: requires-status-and-id-closed.json is not a valid JSON Schema: can't resolve reference https://example.org/schemas/requires-id from id https://example.org/schemas/requires-status-and-id

===== [38] a nested record: the component applied at two levels ==============

The demo's final composite describes a record with a nested
object: a "creator", whose members sit two levels deep in the
instance. The component schema is applied twice by the same
"$ref" -- once to the record, and once, inside the subschema for
"creator", to the creator -- because the component constrains
whichever object it is applied to: each application requires an
"id" member of that object, a string.

Beside the creator's "$ref", the composite tightens the same "id"
the component requires there: a "pattern" demands that the value
open with a URI scheme and a colon. Both constraints on the one
member hold at once. The obvious spelling, "format": "uri", would
change no verdict: both wrappers treat "format" as an annotation
and "pattern" as the enforced form (demo 06). The record's own
"id" stays as the component leaves it -- any string.

Each object is closed by its own "unevaluatedProperties": false,
one in the outer schema object and one in the subschema for
"creator" -- closing the record does not close the creator
(demo 15).

Three instances follow, differing only in the creator. In the
first, the creator's "id" is an https URI, and the instance
passes. In the second it is the plain string "p1", and the
instance is rejected at /creator/id -- a JSON Pointer naming the
nested member (demo 13). In the third the creator gains an
"email" member, and the creator's own closure rejects it at
/creator.

----- [39] the two-level composite -------------------------------------------

$ cat requires-id-status-and-creator-closed.json
{
  "$id": "https://example.org/schemas/requires-id-status-and-creator",
  "allOf": [ { "$ref": "https://example.org/schemas/requires-id" } ],
  "properties": {
    "status": { "type": "string" },
    "creator": {
      "allOf": [ { "$ref": "https://example.org/schemas/requires-id" } ],
      "properties": {
        "id": { "pattern": "^[a-z][a-z0-9+.-]*:" },
        "name": { "type": "string" }
      },
      "required": ["name"],
      "unevaluatedProperties": false
    }
  },
  "required": ["status", "creator"],
  "unevaluatedProperties": false
}

===== [49] a closed composite cannot be widened: the case for keeping components open =====

The composite that requires "id" and "status" closed itself with
"unevaluatedProperties": false, and that closure holds wherever
the composite is applied. The schema below applies the closed
composite in an "allOf" branch and tries to widen it, describing
and requiring one more member, "note". It does not work: the
composite's "unevaluatedProperties" counts only evaluations made
by schemas the composite itself applies (demo 15), and the
"properties" entry for "note" sits outside the composite. To the
composite, "note" is still extra.

The result is a schema no record satisfies: an instance with
"note" is rejected by the composite's closure, and an instance
without "note" fails the "required". Both validators reject both
instances below.

Composition adds requirements and never removes them, so a schema
that closes itself is a final product: another composite can
tighten what it already describes, but no composite can add a
member through it. That is the case for the shape this demo began
with: keep component schemas open, and close only the schema
meant to be used, not built on.
