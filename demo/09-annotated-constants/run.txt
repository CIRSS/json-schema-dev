
===== two ways to say 'one of these exact values' ============================

A fixed set of allowed values is usually written as an enum. There is a
second spelling: oneOf over subschemas that each pin a single value with
const. The two schemas below define the same set — draft and final — and
the demo's first job is to show they are the same predicate: every verdict
that follows agrees across both schemas and both validators.

What the oneOf spelling buys is a place to put prose. An enum is a bare
list; a const subschema is a schema, so each value can carry its own
description saying what choosing it means. The documentation lives next to
the value it documents and travels with the schema into editors, viewers,
and generated docs.

===== the enum schema ========================================================

$ cat schema-enum.json
{"enum": ["draft", "final"]}

===== the annotated oneOf schema =============================================

$ cat schema-oneof.json
{
  "oneOf": [
    { "const": "draft", "description": "not yet reviewed; content may change" },
    { "const": "final", "description": "reviewed and frozen; content is fixed" }
  ]
}

===== a value in the set =====================================================

$ cat instance-known.json
"draft"

===== jsonschema (Python): enum, known =======================================

$ jsonschema-validate --schema schema-enum.json --instance instance-known.json
VALID

===== ajv (JavaScript): enum, known ==========================================

$ ajv-validate --schema schema-enum.json --instance instance-known.json
VALID

===== jsonschema (Python): oneOf, known ======================================

$ jsonschema-validate --schema schema-oneof.json --instance instance-known.json
VALID

===== ajv (JavaScript): oneOf, known =========================================

$ ajv-validate --schema schema-oneof.json --instance instance-known.json
VALID

===== the same rejection, at different levels of detail ======================

A value outside the set, against both schemas. All four runs reject it, so
the two spellings really are interchangeable as predicates. The error
output is where they part: the enum failure can name the allowed list in
one line, while the oneOf failure reports each branch's disappointment
separately before concluding. That verbosity is the cost of the annotated
form, and a message map or report layer pays it, not the schema author.

===== a value outside the set ================================================

$ cat instance-unknown.json
"banana"

===== jsonschema (Python): enum, unknown =====================================

$ jsonschema-validate --schema schema-enum.json --instance instance-unknown.json
INVALID: 'banana' is not one of ['draft', 'final']

===== ajv (JavaScript): enum, unknown ========================================

$ ajv-validate --schema schema-enum.json --instance instance-unknown.json
INVALID: must be equal to one of the allowed values

===== jsonschema (Python): oneOf, unknown ====================================

$ jsonschema-validate --schema schema-oneof.json --instance instance-unknown.json
INVALID: 'banana' is not valid under any of the given schemas

===== ajv (JavaScript): oneOf, unknown =======================================

$ ajv-validate --schema schema-oneof.json --instance instance-unknown.json
INVALID: must be equal to constant
INVALID: must be equal to constant
INVALID: must match exactly one schema in oneOf
