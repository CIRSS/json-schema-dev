===== [1] what $id is for ====================================================

$id declares the identity of a schema — a URI that names it. It is an
identifier, not a location: nothing is ever fetched from it, and it may
point at a host that does not exist.

Its only job is to be the base URI that $ref values resolve against. So a
schema whose $refs are all fragment-only, like #/$defs/named, never
consults its $id at all, and can carry one, or not, with no difference in
behaviour. The first two schemas below make that concrete.

Every instance in this demo is the same object, so that only the schema's
identifiers vary.

----- [2] the instance -------------------------------------------------------

$ cat instance.json
{
  "a": "hello"
}

===== [3] inert: an $id that nothing resolves against ========================

Two schemas, identical but for the presence of an $id — and that $id names
a host that could not be reached even if something tried. Same verdict.

----- [4] no $id at all ------------------------------------------------------

$ cat schema-no-id.json
{
  "$defs": {
    "named": { "properties": { "a": { "type": "string" } } }
  },
  "$ref": "#/$defs/named"
}

----- [5] jsonschema (Python): no $id ----------------------------------------

$ jsonschema-validate --schema schema-no-id.json --instance instance.json
VALID

----- [6] ajv (JavaScript): no $id -------------------------------------------

$ ajv-validate --schema schema-no-id.json --instance instance.json
VALID

----- [7] an $id at an unreachable URI ---------------------------------------

$ cat schema-unreachable-id.json
{
  "$id": "https://nowhere.invalid/this/is/never/fetched",
  "$defs": {
    "named": { "properties": { "a": { "type": "string" } } }
  },
  "$ref": "#/$defs/named"
}

----- [8] jsonschema (Python): unreachable $id -------------------------------

$ jsonschema-validate --schema schema-unreachable-id.json --instance instance.json
VALID

----- [9] ajv (JavaScript): unreachable $id ----------------------------------

$ ajv-validate --schema schema-unreachable-id.json --instance instance.json
VALID

===== [10] load-bearing: naming a subschema so $ref can address it ===========

An $id inside $defs does something different: it declares that subschema to
be a schema resource in its own right, with its own identity, which $ref
can then target by URI instead of by JSON Pointer.

$anchor does the same job more cheaply. It attaches a plain-name fragment
to a subschema without making it a separate resource, reached as #named.

Both schemas below constrain a to be a number, so the string instance is
rejected — which is how you can tell the reference resolved rather than
being quietly skipped. A $ref that went nowhere would not produce this.

----- [11] $id on the subschema, $ref by URI ---------------------------------

$ cat schema-subschema-id.json
{
  "$defs": {
    "named": {
      "$id": "https://example.org/named",
      "properties": { "a": { "type": "number" } }
    }
  },
  "$ref": "https://example.org/named"
}

----- [12] jsonschema (Python): $ref by URI ----------------------------------

$ jsonschema-validate --schema schema-subschema-id.json --instance instance.json
INVALID: /a: 'hello' is not of type 'number'

----- [13] ajv (JavaScript): $ref by URI -------------------------------------

$ ajv-validate --schema schema-subschema-id.json --instance instance.json
INVALID: /a: must be number

----- [14] $anchor, $ref by plain name ---------------------------------------

$ cat schema-anchor.json
{
  "$defs": {
    "named": {
      "$anchor": "named",
      "properties": { "a": { "type": "number" } }
    }
  },
  "$ref": "#named"
}

----- [15] jsonschema (Python): $ref by anchor -------------------------------

$ jsonschema-validate --schema schema-anchor.json --instance instance.json
INVALID: /a: 'hello' is not of type 'number'

----- [16] ajv (JavaScript): $ref by anchor ----------------------------------

$ ajv-validate --schema schema-anchor.json --instance instance.json
INVALID: /a: must be number

===== [17] the footgun: a relative $ref against an $id =======================

Here is why $id is worth understanding even when you are not composing
across documents. The schema below declares an $id and then writes $ref as
the bare word "named", intending the $def of that name.

It is not a fragment, so it is not looked up inside the document. It is a
relative URI reference, resolved against the $id — yielding
https://example.org/schemas/named, a document neither validator has and
neither will go looking for. The $def sitting right there is never
consulted.

Both report it as an error rather than a verdict, and exit 2. Note that the
two disagree about when they notice: Ajv resolves references while
compiling the schema and calls it an invalid schema, whereas jsonschema
resolves lazily during validation, so the failure arrives later and is
described differently. Same conclusion, different stage.

----- [18] a relative $ref ---------------------------------------------------

$ cat schema-relative-ref.json
{
  "$id": "https://example.org/schemas/root",
  "$defs": {
    "named": { "properties": { "a": { "type": "string" } } }
  },
  "$ref": "named"
}

----- [19] jsonschema (Python): relative $ref --------------------------------

$ jsonschema-validate --schema schema-relative-ref.json --instance instance.json
jsonschema-validate: error: schema-relative-ref.json contains an unresolvable $ref: Unresolvable: named

----- [20] ajv (JavaScript): relative $ref -----------------------------------

$ ajv-validate --schema schema-relative-ref.json --instance instance.json
ajv-validate: error: schema-relative-ref.json is not a valid JSON Schema: can't resolve reference named from id https://example.org/schemas/root
